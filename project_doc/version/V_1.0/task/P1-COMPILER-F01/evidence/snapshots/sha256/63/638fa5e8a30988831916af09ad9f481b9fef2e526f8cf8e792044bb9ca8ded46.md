## 2. 背景与问题

### 2.1 当前行为与证据

1. 当前配置解析与运行事实存在直接写入全局 Config 的历史实现，难以在同一 JVM 中隔离多个配置上下文；
2. `dec-expand-declaration` 是临时项目，与目标 System 核心运行时不存在必须保留的依赖，但旧规划曾把它当作可迁移能力来源；
3. 用户提供的真实配置契约位于 `dec-demo/src/main/resources/mix`，由 `orm-config.xml` 发现 Data、View、System 和 Business，System 再间接发现 Rule；
4. 当前缺少一个格式无关、强类型、可诊断、可重复摘要且不可变发布的统一编译边界；
5. 当前 R03 实物清单与源图证据见 `DEC_COMPILER_mix_contract_inventory.md`；
6. R02 将 Information 放在 BusinessScope 中，并让 user System 为识别 `OrderInfo.user` 同时声明 `UserInfo` 与 `OrderInfo`，导致 Information 所有权、System View 边界和共享模型访问关系不清晰；
7. R03 建立了显式 `model-access/ref`，R04 已确认 `ref@property` 对 `view@target-main` 与 View property 的解析优先级；
8. 当前实物包含 `user`、`order`、`payment`、`common` 四个 System，其中 `common` 只声明跨 System expression Information，不拥有 Data、View、RuleView 或 ModelAccess。

### 2.2 需要解决的问题

1. 消除临时 declaration 模块与目标 `mix` 模型并存造成的双模型、双上下文和错误迁移边界；
2. 将配置加载拆分为可验证的源发现、格式前端、Raw 定义、编译 Pass、不可变模型和 EngineContext；
3. 保证跨文件引用、重复定义、未知引用、路径逃逸和不安全解析能够产生稳定、可追溯的 Diagnostic；
4. 明确 P1 与 P2～P7 的阶段边界，禁止在 P1 中隐式实现运行语义；
5. 在不建立第二事实源的前提下，为旧核心 Data/View/Rule 读取提供有限只读过渡；
6. 将 Information 归属收敛到 System，并以显式 `model-access/read|write/ref` 表达共享模型路径与 System 本地 View 的对应关系；
7. 明确 `read|write@path` 为源路径、`ref@property` 为目标选择器，并规定 target-main 优先、property path 回退的确定性解析顺序；
8. 明确普通 System expression 与 `common` 跨 System expression 的所有权、引用、Deferred 和失败边界。

## 3. 需求目标

1. 建立“源图发现 → 格式前端 → RawDefinitionSet → 编译 Pass → CompiledModelSet → EngineContext”的统一编译主线；
2. 以实际 `mix` fixture 证明 Data、View、System、Rule、Business 及其嵌套定义可被确定性发现、解析和建立符号；
3. 建立强类型 Key、稳定 Diagnostic、不可变 Registry、显式 DeferredDefinitionRegistry 和稳定摘要；
4. 允许同一 JVM 创建多个互不污染的不可变 EngineContext；
5. 整体退役 `dec-expand-declaration`，不抽取、不迁移、不建立 Adapter；
6. 保留 P2～P7 的明确扩展接缝，但不提前实现其运行语义；
7. 保证 BusinessScope 仅组织跨 System 的 Directory/Action/Produce，Information 只能引用所属 System 声明的 View；
8. 保证跨多个 System 的 Information expression 只由 `common` System 组合 system-qualified InformationKey；
9. 保证 ModelAccess selector 首先匹配目标 View 的 `target-main`，未匹配时才精确解析 property path。

## 6. 功能详细需求

### 6.1 P1-COMPILER-F01 统一 `mix` 编译骨架

#### 6.1.1 功能目标

将真实 `mix` 配置确定性转换为可诊断、可摘要、不可变的 `CompiledModelSet` 和 `EngineContext`，同时明确后续阶段的 Deferred 边界。

#### 6.1.2 角色与权限

- 配置作者只能通过受支持的来源和格式提供配置；
- 编译调用方只能读取编译结果和 Diagnostic，不得修改 Registry；
- 旧核心调用方只能通过 `CoreConfigProjection` 读取 Data/View/Rule 投影；
- 任何调用方都不得注册全局 current Context。

#### 6.1.3 前置条件

- 调用方提供根 `DocumentSource` 和受支持的 SourceProvider；
- 格式前端、安全解析策略和编译选项已显式配置；
- 输入源位于允许根路径内且 sourceId 可规范化。

#### 6.1.4 正常流程

1. 解析根配置并构建 `MixSourceGraph`；
2. 各格式前端转换为统一 Canonical 节点；
3. 构建 `RawDefinitionSet` 并注册强类型符号；
4. 解析 P1 可确认的引用，将后续语义显式登记为 Deferred；
5. 无 ERROR 时发布不可变 `CompiledModelSet` 和 `EngineContext`。

#### 6.1.5 业务规则

- BR-P1-001：`mix/orm-config.xml` 是 fixture 根入口，但编译器不得硬编码 `dec-demo` 或 `mix` 路径；
- BR-P1-002：源发现必须区分根引用、目录文件集、显式文件和 System 间接 Rule 文件；
- BR-P1-003：目录文件集按标准化 sourceId 排序，文件系统枚举顺序不得影响结果；
- BR-P1-004：发现顺序可以分阶段，语义解析必须允许跨文件前向引用；
- BR-P1-005：RuleViewKey 预留 `(SystemKey, ruleViewName)`，并校验 System 归属、RuleView `system` 属性及 RuleView `view-ref` 属于该 System 的 `view-info`；
- BR-P1-006：BusinessScopeKey 仅作用于 Directory/Action/Produce 的跨 System 编排命名空间；InformationKey 使用 `(SystemKey, localInformationName)`，不得携带 BusinessScopeKey；
- BR-P1-007：P1 完整编译 Data/View 结构和 P1 可验证的 RuleView、System-owned Information 符号；System ModelAccess、Information 求值、Directory、Action、Produce 的运行语义进入 Deferred Registry；
- BR-P1-008：DeferredDefinition 必须说明 requiredStage、reason、SourceRef 和已解析的类型引用，禁止静默忽略；
- BR-P1-009：存在 ERROR 时不得发布 `CompiledModelSet` 或 `EngineContext`；
- BR-P1-010：同义输入、稳定选项和版本产生相同 semanticDigest；sourceDigest 单独反映原始内容；
- BR-P1-011：EngineContext 实例级、不可变，不提供全局 current Context；
- BR-P1-012：`CoreConfigProjection` 只读、deprecated，不注册、不删除、不修改事实；
- BR-P1-013：XML 禁止外部实体和网络解析；YAML 禁止任意 Java 类型构造；
- BR-P1-014：`dec-expand-declaration` 不得出现在仓库、Reactor、依赖树、ServiceLoader、反射字符串或发布 artifact 中；
- BR-P1-015：Business 文件必须作为普通配置源解析，不能触发独立模块加载或旧 declaration runtime；
- BR-P1-016：Information 必须定义在 `<system>` 的 `<information-info>` 内，名称为 System 内局部名称；BusinessScope 不得出现 `<information-info>` 或 `<information>`；普通 System 的 expression 只能组合本 System InformationKey，跨多个 System 的 expression 必须由 `common` System 拥有；
- BR-P1-017：带 `view-ref` 的 Information 只能引用所属 System `view-info` 中声明的 View；带 `rule-ref` 的 Information 只能引用所属 System 的 RuleView；
- BR-P1-018：共享模型的 `<read>`/`<write>` 路径可以包含一个或多个 `<ref view="..." property="..."/>`；`read|write@path` 表示共享模型源路径，`ref@view` 必须指向当前 System View，二者即使同名也不得混为一个字段；
- BR-P1-019：BusinessScope 和 `common` expression 使用 `{systemName}.{informationName}` 引用 System-owned Information；`common` 只允许 expression Information 且不拥有 Data、View、RuleView 或 ModelAccess。未知 System、未知局部名称、未限定引用、普通 System 跨 System 引用或 `common` 非 expression 成员必须产生 ERROR；
- BR-P1-020：`ref@property` 是目标 View 选择器：先与目标 View 的 `target-main` 做区分大小写的完整匹配；仅在未匹配时，才按点分隔 property path 在该 View 属性树中逐段精确查找。两步均失败、路径穿越非复合属性、重复或多候选时产生 ERROR；禁止模糊匹配、全局 View 搜索和静默降级。

#### 6.1.6 输入与输出约束

- 输入：显式根 Source、允许的文件或 classpath 来源、受支持 XML/YAML 节点；
- 输出：成功时返回不可变模型、Context、摘要和非错误 Diagnostic；失败时只返回 Diagnostic 与失败状态，不发布新 Context。

#### 6.1.7 状态、幂等、并发与事务语义

- 状态：`CREATED → SOURCES_DISCOVERED → PARSED → RAW_BUILT → STRUCTURALLY_VALIDATED → SYMBOLS_REGISTERED → REFERENCES_RESOLVED → GRAPH_PREPARED → SEMANTICALLY_VALIDATED → PUBLISHED | FAILED`；
- 幂等：相同源内容、选项和编译器版本产生相同 semanticDigest；
- 并发：不同 CompilationSession 与 EngineContext 不共享可变注册表；
- 事务/部分失败：编译发布采用全有或全无；存在 ERROR 时保留调用方旧 Context，不做部分替换。

#### 6.1.8 异常与禁止副作用

- 不得因未知节点、未知引用、重复 Key、Information/View 归属冲突或 ModelAccess 映射冲突而静默继续发布；
- 不得访问网络、解析外部实体或逃逸允许根路径；
- 不得修改全局 Config、旧 Context、输入 DOM/YAML 节点或已发布 Registry；
- 不得因为删除临时模块而复制旧 declaration runtime 到新模块。

## 9. 验收标准

### AC-P1-COMPILER-001 实物源图发现

Given 用户提供的 `dec-demo/src/main/resources/mix` 和可注入的根 SourceProvider
When 执行 `MixSourceResolver`
Then 发现 10 个 XML 文件，并形成 root→data/view/system/business、system→rule 的有类型边，路径顺序稳定
And 生产代码不硬编码项目目录或 `mix` fixture 路径。

### AC-P1-COMPILER-002 统一前端与 RawDefinitionSet

Given 同义 XML/YAML 最小 fixture 和真实 XML `mix`
When 通过统一 Canonical/Raw 契约解析
Then 真实 fixture 中 5 Data、2 View、4 System、14 RuleView、1 BusinessScope、16 Information、5 Directory、8 Action、4 Produce 均进入 RawDefinitionSet
And 编译结果不持有 DOM 或 SnakeYAML 节点。

### AC-P1-COMPILER-003 强类型符号与引用

Given 包含合法前向引用、重复定义、未知目标和 System 归属冲突的 fixture
When 执行符号注册和引用解析
Then Data/View/System/RuleView/BusinessScope/Information/Directory 使用不同 Key，其中 InformationKey 为 `(SystemKey, localName)`，合法引用成功，非法输入产生稳定 ERROR
And 不用字符串 Key 混用、不以 BusinessScopeKey 标识 Information，也不静默覆盖重复定义。

### AC-P1-COMPILER-004 Deferred 边界

Given 包含 System-owned Information、System ModelAccess、BusinessScope Directory、Action 和 Produce 的真实 `mix` 配置
When P1 完成结构和引用编译
Then 后续阶段语义均显式登记为 Deferred，包含 requiredStage、reason、SourceRef 和已解析类型引用
And P1 不执行这些语义，也不把它们伪装为完整编译。

### AC-P1-COMPILER-005 不可变发布与摘要

Given 两次相同输入编译、两个并存 Context 以及一组包含 ERROR 的输入
When 执行编译和发布
Then 相同输入摘要稳定，成功 Context 互不污染，错误输入不发布新模型
And 已发布集合不可修改，失败不会替换调用方旧 Context。

### AC-P1-COMPILER-006 旧核心只读投影

Given 新 Context 中已编译的 Data/View/Rule 事实
When 旧核心调用方通过 `CoreConfigProjection` 读取
Then 获得与新 Context 一致的只读视图，所有写操作明确拒绝
And 不创建独立注册表、双写或 declaration 兼容层。

### AC-P1-COMPILER-007 临时模块整体退役

Given 默认 Reactor、仓库源代码、服务发现、反射字符串和发布 artifact 清单
When 删除 `dec-expand-declaration` 并执行残留扫描与必要构建
Then module、依赖、类、服务和 artifact 均无残留，必要场景只基于 `mix` 重写
And 不存在 `LegacyDeclarationAdapter`、复制实现或运行时双轨。

### AC-P1-COMPILER-008 System-owned Information 与跨 View 映射

Given 实际 `mix` 中 user、order、payment、common 四个 System，以及共享 `OrderInfo` 与本地 `UserInfo`
When 构建 System、Information、RuleView 和 ModelAccess 的结构及类型引用
Then 16 个 Information 全部归属 System，`common.paySuccess` 与 `common.payError` 只以 expression 组合 system-qualified InformationKey，带 `view-ref` 的 Information 与 RuleView 只引用本 System View，BusinessScope 不定义 Information，且 `OrderInfo.user` 通过 `<ref view="UserInfo" property="user"/>` 显式映射到 `UserInfo.user`
And user System 不直接声明 `OrderInfo`，普通 System 跨 System expression、`common` 非 expression 成员、未知/歧义映射、跨 System View 引用或未限定 Information 引用均阻断发布。

### AC-P1-COMPILER-009 ModelAccess target-main 优先解析

Given `OrderInfo.user` 的 `<read path="user">`、`<ref view="UserInfo" property="user"/>` 以及 `<view name="UserInfo" target-main="user">`
When 编译器解析 ModelAccess ref 的目标选择器
Then `read@path="user"` 保持为共享模型源路径，`ref@property="user"` 首先命中 `UserInfo.target-main="user"` 并绑定到 View 根目标
And 当 selector 不匹配 target-main 时，只在 `UserInfo` 的 property 树中按路径精确查找；未匹配或歧义必须产生 ERROR，不得使用 `root-property`、模糊匹配或跨 View 搜索。

## 10. 非功能要求

### 10.1 性能

- P1 不设置绝对性能门槛，但必须暴露 discovery、parse、pass、digest 的计时接缝；
- 目录排序和摘要计算必须确定性，不能依赖并行调度顺序。

### 10.2 安全与权限

- XML 禁止外部实体和网络解析；YAML 禁止任意 Java 类型构造；
- `MixSourceResolver` 阻止路径逃逸、重复 sourceId 和不允许的 URI scheme。

### 10.3 可靠性、一致性与恢复

- 所有发布集合做防御性复制；
- ERROR 采用全有或全无发布；
- 临时模块删除可通过版本控制回退，但不保留运行时双轨。

### 10.4 审计与可观测性

- Diagnostic 排序键固定为 sourceId、line、column、code、entityKey、pass；
- 每个 DeferredDefinition、错误和源图边均保留 SourceRef；
- sourceDigest 与 semanticDigest 分离记录。

### 10.5 兼容与历史数据

- Java 8 源码兼容；
- 旧核心兼容仅限 Data/View/Rule 只读投影；
- 不兼容旧 declaration runtime、XML/YAML 或 Adapter。

## 11. 模块职责边界

### 11.1 `dec-core-compiler` 模块

负责：

- SourceGraph、Canonical/Raw、符号注册、P1 引用解析、Deferred 登记、Diagnostic、摘要和不可变发布。

不负责：

- P2～P7 运行语义、SQL/MySQL、demo fixture 定位、业务代码生成和旧 declaration runtime。

### 11.2 协作模块

| 模块 | 负责内容 | 输入/输出业务事实 | 失败责任 |
|---|---|---|---|
| XML/YAML frontend | 安全解析并输出 Canonical 节点 | Source → CanonicalDocumentNode | 格式、安全解析错误 |
| `dec-core-context` | 承载不可变 EngineContext 和旧核心只读投影边界 | CompiledModelSet → Context/Projection | 不可变性与读取契约 |
| `dec-core-starter` | 组装 SourceProvider、Frontend 和 Compiler | 根 Source 与编译选项 → CompilationResult | 组装和启动失败 |
| `dec-demo` | 提供真实 `mix` fixture 和契约测试 | fixture 与断言，不进入核心依赖 | fixture 漂移和测试失败 |

### 11.3 协作边界

依赖方向必须从 starter/demo/frontends 指向 compiler/context 的公共契约；compiler 不反向依赖 demo、数据库或具体格式实现。Business 只是 Directory/Action/Produce 的跨 System 编排作用域，不拥有 Information，也不是模块、Context 或执行器。
