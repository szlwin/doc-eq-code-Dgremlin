## 3. 源发现与编译流程

### 3.1 有类型源图

| 边类型 | 来源 | 目标 | P1 要求 |
|---|---|---|---|
| `ROOT_DATA_FILESET` | `orm-config.xml` | `data/` | 规范化 sourceId 后稳定排序 |
| `ROOT_VIEW_FILESET` | `orm-config.xml` | `view/` | 目录枚举顺序不影响语义摘要 |
| `ROOT_SYSTEM_FILE` | `orm-config.xml` | `systems.xml` | 显式单文件引用 |
| `ROOT_BUSINESS_FILE` | `orm-config.xml` | `order-business.xml` | 普通配置源，不加载独立 runtime |
| `SYSTEM_RULE_FILE` | `systems.xml#system` | rule XML | 保留来源 SystemKey 并校验 RuleView.system |

### 3.2 L0/L1/L2 分层流程

- **L0：编译并发布配置模型**：输入受控文档源，输出不可变 `EngineContext` 或失败 Diagnostic。
- **L1：发现 → 解析 → 建 Raw → 注册符号 → 解析引用 → 登记 Deferred → 验证 → 摘要 → 发布**。
- **L2 关键路径**：
  1. 发现失败：停止，不解析未知源；
  2. 结构/引用失败：收集稳定 ERROR，不发布；
  3. Deferred 登记：保留 requiredStage、reason、SourceRef 和已解析 Key；
  4. 发布失败：调用方旧 Context 保持可见，不做部分替换；
  5. 重试：相同输入重新编译，不能复用失败 Session 的可变状态。

该流程是编译基础设施流程，不是业务订单状态流；不创建项目级 `FLOW-*`。Review 使用本文流程表、测试矩阵和依赖影响作为可追踪流程证据。

## 4. Information 所有权分析

### 4.1 普通 System

`user`、`order`、`payment` 为普通 System：

1. Information 使用局部名称，完整 Key 为 `(SystemKey, localName)`；
2. 带 `view-ref` 的 Information 只能引用本 System `view-info` 声明的 View；
3. 带 `rule-ref` 的 Information 只能引用本 System 的 RuleView；
4. expression 可以组合本 System InformationKey；
5. expression 若引用其它 SystemKey，必须报所有权错误，不得在普通 System 中直接求值；
6. `rule-data`、`change-data`、`view-ref`、`rule-ref` 的实际识别/物化/执行语义分别 Deferred 到 P2/P3/P4。

### 4.2 `common` System

`common` 是组合所有者，不是共享运行容器。其静态不变量：

- `data-info`、`view-info`、`rule-file-info` 为空或不存在；
- 不得声明 `model-access-info`；
- Information 必须且只能使用 `expression`；
- 不得携带 `view-ref`、`rule-ref`、`rule-data`、`change-data`；
- expression 中每个引用必须是 `{system}.{information}` 完整限定 Key；
- 引用目标必须存在且不能是未注册 System；
- P1 只解析 expression token、逻辑结构和 Key；布尔求值、依赖 DAG、循环检测、缓存与失效属于 P3。

当前实物：

| InformationKey | Expression | 直接依赖 |
|---|---|---|
| `common.paySuccess` | `payment.success and order.paySuccessStatus` | `payment.success`、`order.paySuccessStatus` |
| `common.payError` | `payment.error and order.payErrorStatus` | `payment.error`、`order.payErrorStatus` |

### 4.3 BusinessScope 引用

BusinessScope 不拥有 Information，只消费完整限定 Key：

- `common.paySuccess`；
- `common.payError`；
- 其它 `user.*`、`order.*`、`payment.*`。

裸 `payError`、未知 `common.x`、未知 System 或把 `payment.error and order.payErrorStatus` 直接定义回 BusinessScope 均为 ERROR。

## 5. ModelAccess selector 确定性规则

### 5.1 源与目标分离

- `model-access@model-ref`：共享模型；
- `read|write@path`：共享模型源路径；
- `ref@view`：当前 System 已声明的目标 View；
- `ref@property`：目标 View 内的 selector；
- source path 与 selector 即使同名也属于不同字段，不得互相推导。

### 5.2 解析算法

对每个 `<ref view="V" property="P"/>`：

1. 校验 `V` 在当前 System 的 `view-info` 中唯一声明；
2. 载入 `V` 的结构，不跨 View 搜索；
3. 若 `P` 与 `V.target-main` 区分大小写完整相等，绑定 View 根目标；
4. 否则把 `P` 按 `.` 分段，在 `V` 的 property 树逐段精确查找；
5. 中间段不是复合属性、任一段缺失、出现重复候选或同一 source path 的 selector 重复/冲突时产生 ERROR；
6. 成功结果保存显式 `ModelAccessBinding(sourceModel, sourcePath, system, targetView, targetKind, targetPath)`；
7. 不允许 `root-property`、前缀/后缀/大小写不敏感匹配、同名猜测、跨 View 搜索或失败后降级。

### 5.3 多 ref 规则

- 一个 `read`/`write` 可以声明多个 `ref`，每个 ref 独立解析；
- 多 ref 必须产生不同且无冲突的绑定；
- 完全重复 ref 不是幂等声明，而是重复配置 ERROR；
- 同一 source path 指向同一 View 的 root 与其内部 property，若写集合重叠，标记冲突并 Deferred 给 P2 权限分析前先阻断不确定结构；
- `read path="*"` 不隐式生成所有 View 映射，只有显式 ref 才形成跨 View binding。

## 6. Diagnostic 需求分类

P1 必须提供稳定 code、SourceRef、entityKey 和 pass。code 名称在设计阶段可形成枚举，但语义至少覆盖：

| 语义 | 建议稳定 code | 阻断 |
|---|---|---|
| 未知/重复 System 或 InformationKey | `MIX-REF-INFORMATION-UNKNOWN` / `MIX-SYMBOL-INFORMATION-DUPLICATE` | 是 |
| 未限定 Information 引用 | `MIX-REF-INFORMATION-UNQUALIFIED` | 是 |
| 普通 System 跨 System expression | `MIX-REF-INFORMATION-CROSS-SYSTEM-OWNER` | 是 |
| `common` 声明非 expression 成员 | `MIX-STRUCT-COMMON-UNSUPPORTED-MEMBER` | 是 |
| View 未由当前 System 声明 | `MIX-REF-VIEW-NOT-DECLARED` | 是 |
| RuleView 来源 System 与属性不一致 | `MIX-REF-RULE-SYSTEM-MISMATCH` | 是 |
| selector 未命中 | `MIX-REF-MODEL-ACCESS-TARGET-NOT-FOUND` | 是 |
| selector 重复或歧义 | `MIX-REF-MODEL-ACCESS-TARGET-AMBIGUOUS` | 是 |
| Deferred 缺少 requiredStage/SourceRef | `MIX-DEFERRED-INCOMPLETE` | 是 |
| ERROR 后仍尝试发布 | `MIX-PUBLISH-WITH-ERROR` | 是 |

Diagnostic 排序固定为 `sourceId, line, column, code, entityKey, pass`，从而保证重跑和并行 Pass 不改变输出顺序。

## 7. 横切边界

### 7.1 权限与安全

- SourceProvider 只访问允许的 URI scheme 与根路径；
- XML 禁止外部实体、DTD 网络访问；YAML 禁止任意 Java 类型；
- System View、RuleView、Information 和 ModelAccess 所有权在 P1 做结构验证，P2 再完成读写权限语义；
- Diagnostic 不输出凭据正文或不受控绝对路径。

### 7.2 幂等、并发与事务

- 相同 source 内容、编译器版本和选项产生相同 semanticDigest；
- CompilationSession、RegistryBuilder 和 DiagnosticCollector 均为实例级；
- 不同 Context 不共享可变 Registry；
- 发布为全有或全无；任何 ERROR 都不替换旧 Context；
- 重试从新的 Session 开始，不复用上次失败的半成品。

### 7.3 审计与恢复

- 每个 source、RawDefinition、binding、Deferred 和 Diagnostic 保留 SourceRef；
- `sourceDigest` 与 `semanticDigest` 分离；
- 删除 `dec-expand-declaration` 不迁移运行状态，恢复只依赖 Git；
- 已运行的旧 Context 不被强制修改；新编译失败时继续使用调用方显式持有的旧 Context；
- 不保留运行时双轨或自动回退到旧 declaration parser。

## 9. 跨模块实现映射

| 步骤 | Owner | 输入 | 输出 | 失败与恢复 |
|---|---|---|---|---|
| Source discovery | `dec-core-compiler` | 根 DocumentSource | MixSourceGraph | 停止发现；不访问未授权源 |
| XML/YAML frontend | 各 frontend | SourceRef/bytes | CanonicalDocumentNode | Diagnostic；不写全局 Config |
| Raw build / symbol register | `dec-core-compiler` | Canonical nodes | RawDefinitionSet/SymbolTable | 收集 ERROR；无发布 |

| Atomic exposure | `dec-core-starter` | successful EngineContext | 调用方显式持有的新 Context | 失败继续保留旧 Context |

## 11. 风险与停止条件

- **R1 Scope creep**：把 common expression 求值或 cycle detection 提前到 P1；措施：只解析 AST/Key，求值和 DAG Deferred 到 P3。
- **R2 所有权回退**：把组合信息重新放入 BusinessScope；措施：结构校验 + fixture 负向测试。
- **R3 selector 猜测**：用同名或跨 View 搜索掩盖缺失映射；措施：target-main/精确 path 两步算法，失败即 ERROR。
- **R4 Deferred 黑洞**：缺 requiredStage 或未被后续阶段消费；措施：完整字段和阶段消减测试。
- **R5 双写/双运行时**：CoreConfigProjection 或 declaration Adapter 重新产生第二事实源；措施：只读 API 与残留扫描。
- **R6 构建环境**：Maven 镜像不可达；措施：保留命令失败 Evidence，先完成不依赖网络的 XML/Python/文档门禁，网络恢复后补动态 JUnit。

出现以下任一情况立即停止：恢复 declaration 模块、引入第二 Context、允许 common 拥有 View/RuleView/ModelAccess、允许普通 System 跨 System expression、允许 selector 模糊/跨 View 搜索、提前执行 P2～P7 语义。

## 12. 分析结论

REQCONF-R04 已具备进入业务模型阶段所需的确定边界：

1. 4 个 System 和 16 个 Information 的所有权闭合；
2. `common` 只承载跨 System expression，并只引用完整限定 InformationKey；
3. BusinessScope 不拥有 Information；
4. ModelAccess 的 source path、target View 和 selector 分离，target-main 优先且 property path 精确回退；
5. 所有失败均以稳定 Diagnostic 阻断发布；
6. P1 与 P2～P7 的 Deferred 和跨模块责任明确；
7. 九项 AC 均有正常、边界、失败和恢复测试映射。
