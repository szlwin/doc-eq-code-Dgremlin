## 第一部分：设计正文

### 1. 一页设计摘要

<!-- DESIGN-NARRATIVE-SUMMARY -->
P2 改为两条容易理解的主链路。配置链路负责把 XML/YAML 安全地发布为当前配置；业务链路继续使用现有模型与容器 API。ConfigInfo 在内部关联编译后的 EngineContext，业务调用者不传递 Context 或权限证明。

#### 1.1 改造前后对照

| 维度 | DESIGN-P2-R36 | DESIGN-P2-R38 |
|---|---|---|
| 业务入口 | Guard/Scope/Session/Handle/Capability | DataUtil/ModelLoader/ModelContainer |
| 配置入口 | 编译模型与旧 ConfigInfo 并存 | 候选 ConfigInfo -> Compiler -> EngineContext |
| 发布 | 强 runtime identity 绑定 | ConfigInfo + EngineContext 整体安装 |
| 读取/修改 | 受保护端口和一次性能力 | ModelData 直接读写 |
| 安全底线 | owner、generation、stamp、proof | 定义检查、失败不安装、事务回滚与关闭 |
| 兼容性 | 业务方理解 runtime 对象 | 保持 RuleTests 风格调用 |

#### 1.2 六个关键结论

1. XML/YAML 解析只写候选 ConfigInfo。
2. 编译成功后同一个候选对象绑定 EngineContext，再由 ConfigManager 整体安装。
3. 编译或发布失败时当前配置对象不变。
4. 业务调用固定为 DataUtil -> ModelData -> ModelLoader -> ModelContainer.execute()。
5. context/runtime、model/runtime、starter/access 以及专用测试全部退役。
6. 保持 Java 8、简单规则名、连接提交/回滚/关闭和明确错误。

### 2. 背景、现状与设计目标

<!-- DESIGN-NARRATIVE-CURRENT -->
重型 runtime 模型对普通配置驱动业务增加了过多概念，并且与 dec-demo 的直接调用方式冲突。代码 revision 8b362d5d 已实现候选解析、ConfigInfo 与 EngineContext 对接、明确错误和容器事务收尾，本设计将这些实现事实正式变成 P2 权威设计。

#### 2.2 设计目标与非目标

目标是使配置加载可靠、业务调用简单、错误可定位、数据库资源正确收尾。非目标是字段权限、租户授权、运行时对象身份、一次性能力、脚本沙箱、数据库结构和 HTTP API。

### 4. 目标方案与职责边界

<!-- DESIGN-NARRATIVE-TARGET -->
目标方案把“配置如何安全生效”和“业务如何简单执行”分离。ConfigInfo 是配置所有者，EngineContext 是该配置的编译结果；ConfigManager 只发布完成绑定的整体对象。业务侧复用现有模型 API，不增加上下文或授权参数。

#### 4.1 目标结构

```text
XML / YAML
    -> candidate ConfigInfo
    -> Compiler
    -> EngineContext
    -> ConfigManager.install(ConfigInfo, EngineContext)

business code
    -> DataUtil.createViewData(viewName)
    -> ModelLoader.load(ruleName, modelData, connectionName)
    -> ModelContainer.load(...)
    -> ModelContainer.execute()
```

#### 4.2 组件职责

| 组件 | 输入 | 输出 | 禁止职责 |
|---|---|---|---|
| ConfigInfo | 配置定义、EngineContext | 实例内配置、兼容 Projection | 不负责数据库事务 |
| ConfigManager | candidate + EngineContext | 当前安装 ConfigInfo | 不发布半成品 |
| XML/YAML Parser | 文件 + candidate | 同一 candidate | 不直接替换当前配置 |
| CompilerStarter | candidate + publisher | CompilationResult | 失败时不 install |
| DataUtil | View 名称 | 完整 ViewData | 不创建 runtime 占位对象 |
| ModelLoader | Rule、ModelData、Connection | 执行任务 | 不静默忽略缺失 Rule |
| ModelContainer | 执行任务 | 提交或异常 | 不泄漏连接 |

### 5. 核心流程、状态与失败路径

<!-- DESIGN-NARRATIVE-FLOW -->
主流程始终先形成候选配置，再编译和发布；只有最后一步安装会改变当前配置。业务执行从已安装配置取得定义，任何缺失在数据库副作用前失败，执行异常由 ModelContainer 统一回滚和关闭资源。

#### 5.1 主流程

<!-- DESIGN-FLOW -->
1. ConfigManager 创建线程内候选 ConfigInfo。
2. XML/YAML Parser 通过 parseInto 写入候选对象。
3. CompilerStarter 编译候选对象并请求 Publisher 发布 EngineContext。
4. 发布成功后，候选对象绑定 Publisher 返回的同一个 EngineContext。
5. ConfigManager.install 通过 volatile ConfigInfo 引用整体切换。
6. 后续业务通过已安装 ConfigInfo 查找 View、Rule 和 Connection。
7. ModelContainer 执行任务，成功提交，失败回滚，最终关闭连接。

#### 5.2 关键失败路径

| 失败点 | 失败时序 | 副作用 |
|---|---|---|
| 文件解析失败 | compile 前 | 当前配置不变 |
| 编译诊断失败 | install 前 | 当前配置不变 |
| 发布冲突 | install 前 | 当前配置不变 |
| View/Rule/Connection 缺失 | 数据库副作用前 | 无业务写入 |
| 规则或 SQL 执行失败 | execute 中 | 回滚并关闭 |
| close 失败 | 原始失败已保留后 | 记录收尾异常，不伪造成功 |

#### 5.3 状态与步骤

候选配置状态为 CREATED -> PARSED -> COMPILED -> INSTALLED；任一失败进入 REJECTED。INSTALLED 只有一个入口：compileAndInstall 成功后调用 ConfigManager.install。REJECTED 候选不可成为当前配置。

### 6. 数据与持久化方案

<!-- DESIGN-NARRATIVE-DATA -->
本次不改变数据库结构。配置数据保存在 ConfigInfo 实例内 Map 中，EngineContext 以 volatile 字段绑定到同一 ConfigInfo；当前安装对象由 ConfigManager 的 volatile 引用保存。业务数据持久化仍由 ModelContainer 通过 DataConnection 执行。

#### 6.1 单次请求内的持久化生命周期

| 阶段 | 读取 | 写入 | 保存/回滚 |
|---|---|---|---|
| 配置解析 | XML/YAML | candidate ConfigInfo | 只在内存候选对象 |
| 编译发布 | candidate | EngineContext | 成功后整体 install；失败丢弃 candidate |
| 模型创建 | 当前 ConfigInfo 的 View | ModelData 内存值 | 不涉及数据库 |
| 规则执行 | Rule/Connection/ModelData | 数据库 | 成功 commit；失败 rollback；finally close |

### 7. 接口、交互与兼容策略

<!-- DESIGN-NARRATIVE-COMPATIBILITY -->
对业务调用保持源码兼容。parseInto、compileAndInstall 和 ConfigManager.install 是内部兼容扩展；旧 parse 入口仍可委托新入口。已退役 runtime/access API 不提供适配层。

#### 7.1 页面业务行为

不适用：本需求没有页面。可观察业务行为由 Java 调用结果、异常以及数据库提交/回滚体现。

#### 7.2 事务、并发、幂等与一致性

- ConfigManager.install 使用同步发布和单一 volatile 引用，避免半新半旧。
- 同一文件重复加载可生成新 candidate；只有成功 candidate 生效。
- ModelContainer 维持既有多连接事务收尾，不把配置发布与数据库事务混合。
- 不建立运行时 owner/generation identity；该风险已由用户授权排除。
